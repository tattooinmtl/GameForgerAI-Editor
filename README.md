# GameForgerAI

**Version:** Alpha 0.79

An AI-assisted OpenGL 3D game editor and standalone runtime. This is a CMake
folder project; do not create a Visual Studio solution or select a Visual
Studio project template.

## Requirements

- Windows 10 or 11
- Visual Studio 2026 with **Desktop development with C++**
- Git
- CMake and Ninja components included with Visual Studio
- A graphics driver supporting OpenGL 4.6
- Internet access during the first CMake configure
- An `NVIDIA_API_KEY` and/or `AGNES_AI_API_KEY` in `Game/AI/Providers.local.json` to use the AI features

The `.vsconfig` file allows Visual Studio Installer to detect the required C++
components. CMake downloads pinned versions of GLFW, GLAD, GLM, Dear ImGui,
ImGuizmo, Lua, Assimp, and stb_image into the build directory. They are not
installed globally. Assimp is the largest of these - the first configure/build
after it's added takes noticeably longer while it fetches and compiles.

## Open in Visual Studio 2026

1. Start Visual Studio 2026.
2. Select **Open a local folder**.
3. Open this project folder.
4. Allow CMake configuration to finish.
5. Select `GameForgerEditor.exe` as the startup item if it is not already selected.
6. Press `F5`.

You can also right-click this folder in Explorer and choose **Open with Visual
Studio** when that shell integration is installed.

## Command-line build

Run from a Visual Studio Developer PowerShell:

```powershell
cmake --preset windows-x64
cmake --build --preset editor-debug
.\out\build\windows-x64\Editor\Debug\GameForgerEditor.exe
```

## Generated targets

- `GameForgerEngine`: reusable C++ engine library
- `GameForgerEditor`: Dear ImGui docking editor
- `GameForgerRuntime`: small standalone game runner

## Features

**Viewport & editing**
- 3D viewport with primitive shapes (cube, sphere, cylinder, cone, plane, capsule), lit shading, and a ground grid
- Toolbox panel, first tool: 3D Text Mesh - import a `.ttf`/`.otf` font and type a string to get real extruded 3D glyph geometry (proper triangulated letterforms with holes, e.g. the counters of "A"/"O"/"8", not billboarded/flat text), placed as a normal entity with full Transform/Pivot/Collider/Camera Rig/Scripts/Animation support
- Toolbox, second tool: Cine Camera - a cutscene camera entity, separate from the player/Game view camera, rendered as a small wireframe icon in every viewport. Move it and record keyframes on the Animation tab to author a path, preview it live in a dedicated dockable Cine Camera Preview window, capture that path as a numbered shot in the Storyboard panel, and sequence multiple shots into "Play Movie" playback. Text Mesh/other objects with their own animation enabled play back in sync on the same cutscene timeline, standing in for "attaching" them to the shot
- Toolbox, third tool: Terrain - a real heightmap (not a primitive standing in for one), starts flat with equal headroom to sculpt up or down (heights are 0.5-centered - see Alpha 0.52). Select it and use the Inspector's Terrain section to sculpt height with a brush (Raise/Lower toggle, hold Shift to temporarily use the other one without switching it back, adjustable radius/strength - both directions actually reach the terrain's floor/ceiling now, so canyons/riverbeds/lake bottoms are possible, not just hills), import a grayscale image as a heightmap, or generate one procedurally with Perlin noise (scale/octaves/seed). Picking and the sculpt brush both raycast the actual heightmap surface, not just a bounding box. AI Forge can also create one directly (`create_terrain`, `shape: "mountain"` for an actual sculpted radial peak sized to a requested base/height - used instead of a `cone` primitive for mountain/hill requests)
- Character menu > Import Model (GLB/glTF/FBX/3DS/OBJ/Blend)...: real mesh import via Assimp, not primitives standing in for it. The file is copied into `Game/Models/`, then every mesh in its node hierarchy is flattened (with each node's own transform applied) into one combined mesh on a normal entity - full Transform/Pivot/Collider/Camera Rig/Scripts/Animation support, same as everything else. The camera auto-frames on the model's real bounds right after import. If the file carries skin weights, it imports as a real skinned/skeletal mesh instead: GPU vertex skinning plus the file's own first baked animation clip auto-play (an imported rigged character animates on its own, no setup) - see Known gaps for what that doesn't include yet (no bone list/scrub UI, no manual posing). No materials or textures are imported yet
- Move (W) / Rotate (E) / Scale (R) / Rect (T) / Transform (Y, unified) gizmos, all pivot-aware
- Custom pivot points per object (manual, 3x3 preset grid, or describe it to the AI) - e.g. a door hinge edge
- Multi-tag objects: any number of tags per object, in priority order (the first is primary - e.g. what a "Ground" auto-collider check reads). Reorder (Up/Down), remove, or add a preset (Player/Enemy/Prop/Environment/Trigger/Ground) or free-text custom tag from the Inspector
- Click / Ctrl+click / Shift+click multi-select, in the Hierarchy or the Viewport - Hierarchy selection works during Play too, not just when stopped
- Project panel files are clickable; clicking a `.lua` script opens it in the script editor directly, no need to go through an entity's Inspector first
- Orbit, pan, zoom, true first-person flythrough (right-click + WASD/QE), and Frame Selected (F or Ctrl+F) - once framed, the mouse wheel can zoom all the way in to the selected object's exact center instead of stopping at the usual minimum distance
- Undo/redo (Ctrl+Z / Ctrl+Y, 5 steps), copy/paste (Ctrl+C / Ctrl+V) for objects and scripts, select-all (Ctrl+A), Delete for objects or a focused script

**AI layer**
- AI Forge panel: natural-language prompts planned into typed, validated, previewable editor commands - each prompt sees the current scene's entities, so you can keep re-prompting to add, modify, or remove things by name on top of what's already there (the scene is never wiped except by File > New Scene)
- AI script generation, attached directly to an object from the Inspector
- Presets (Add Script > "Presets: controllers & collider"): a multi-select dropdown for FPS Controller / Third-Person Controller / Rigidbody (each auto-marks the object as a Collider) and/or Collider Only - check any combination and apply them all at once with "Add Selected Presets", next to Close
- AI keyframe-animation generation for one or many selected objects at once
- Local (offline, instant) command syntax still works as a fast path alongside the AI

**Animation & Play mode**
- Manual keyframe recording (continuous Record mode or one-shot), timeline scrubbing, and preview playback
- Play/Stop: a non-destructive sandbox that runs recorded animations live and restores the scene exactly on Stop
- Real Lua 5.4 script execution during Play: every script attached to an object actually runs (`on_start`/`on_update`), sandboxed to `base`/`table`/`string`/`math` (no `io`/`os`/`package`/`debug`, and `dofile`/`loadfile` are also removed from `base` since they read arbitrary files by path independently of those), with entity bindings (get/set position, get/set rotation, forward, right) and keyboard input bindings (`isKeyDown`, `isKeyPressed`, `getAxis`). Script paths are confined to `Game/Scripts/*.lua` and re-validated immediately before every load, so a script can't be attached or executed from outside the project even via a hand-edited scene file
- Basic gravity + AABB collision (script-side): a `self.physics:resolve()` binding pushes a moving script's capsule/box out of any object with its Inspector "Collider" checkbox on, both for standing on platforms (real ground check, not just a fixed plane) and for blocking movement into walls; the FPS/third-person prefabs use it, and so does the Rigidbody preset (falls under gravity and lands on/collides with anything Collider-enabled - for props you want to drop and settle, like a cube). Tagging an object "Ground" turns its Collider on automatically - handy for planes and stairs. World `y = 0` remains a fallback floor if a scene has no Collider objects. This is simple axis-aligned box collision, not general rigidbody physics (no rotation-aware shapes, no physics materials, no colliders pushing each other)
- Scripted in-game camera (`self.camera:setMode("fps" | "third_person")`): the Game view follows whichever entity's script last claimed the camera, first-person at its eyes or third-person trailing behind it; the FPS/third-person prefabs both bind the **C** key to swap between the two live during Play
- Mouse-look: hold Right Mouse over the Game view to look around - in FPS mode the character turns with your view (movement follows it too), in third-person mode the camera orbits the character freely without turning it
- Per-entity Camera Rig in the Inspector (FPS eye height, third-person distance/height/aim-height/angle) - adjusts that entity's scripted camera live, including while Play is running
- Separate Game view panel previewing the scene as-is, independent of the editable Scene viewport

**Editor windows**
- Hierarchy, Inspector, Viewport, Game view, Project (real `Game/` file browser), Console (Info/Warning/Error log), AI Setup, AI Forge, Animation, Toolbox, Cine Camera Preview, Storyboard

**Other**
- Splash screen, window/taskbar icon, and system tray icon from `Game/Branding/logo.jpg`
- Scene save/load with native folder browsing: File > Save Scene (Ctrl+R, quick-saves to the current path) / Save Scene As... (pick any folder) / Open Scene... (Ctrl+O, load any `.json` scene from anywhere) / New Scene (Ctrl+N)

## Known gaps (roadmap to Beta 1.0)

- Model import (GLB/glTF/FBX, via Assimp) has no materials or textures (renders with the entity's own flat `color`, like everything else, since there's no texture pipeline - see below), and flattens the whole file into one combined mesh rather than preserving it as separate sub-objects (this editor's SceneEntity model has no parent-child hierarchy yet). The "Map Humanoid Skeleton..." and "Animation Library..." Character menu items are still inert placeholders
- Collision is simple AABB box vs. box (no rotation-aware colliders, no physics materials, no colliders pushing each other, no sphere/capsule/mesh collider shapes) - not general rigidbody physics
- No placeable Camera entity (Game view uses a fixed default camera)
- Skeletal animation (Alpha 0.52) is playback-only: an imported rigged model auto-plays its own single baked-in clip via GPU skinning, but there's no bone-hierarchy list/scrub UI, no clip selection (only the file's first animation is used), and no manual bone posing/rig-editing - a deliberate first-pass scope choice, not a limitation of the underlying data (the importer already extracts the full bone hierarchy and track data, a UI just isn't built on top of it yet)
- Undo/redo covers entity/transform/script state; it does not cover camera, selection, or AI Setup changes
- The Viewport's selection outline is a fixed box sized for primitives - it doesn't wrap a Text Mesh's actual (variable-length) bounds correctly yet, though picking/clicking a Text Mesh does use its real geometry
- Text Mesh only lays out left-to-right with explicit `\n` line breaks - no text wrapping, alignment, or bidirectional/vertical scripts
- A Storyboard "shot" is just a Cine Camera's own captured keyframe path, not a full scene snapshot; the shot list is in-memory only and is not saved with the scene yet; there's no per-shot field-of-view (all viewports use the same fixed 50° perspective); "attaching" text/objects to a cutscene means giving them their own independent animation that ticks on the same timeline, not a true parent-child/rigid transform attachment
- Tags are per-object only - scripts and other non-entity things don't carry their own tags. Reordering an object's tag priority isn't undoable (same as Storyboard shots and Animation keyframes - direct editor bookkeeping, not routed through the command bus)
- No texture-mapping pipeline yet - all geometry (including Terrain) is flat vertex-colored, no UVs, no texture sampling in the shader. Terrain's `texturePath` field exists in the data model but isn't rendered yet. This blocks texture splatting, road painting, and anything texture-based
- Terrain has no multi-layer texture blending, road painting, or tree/grass placement brushes yet (all planned follow-ups to the base heightmap system); sculpting isn't undoable (same direct-bookkeeping reasoning as tag reordering); resolution/world size can't be changed after creation from the Inspector (would require resampling the heights array, not yet implemented); no LOD, so a very high resolution will be slow to sculpt/render

Do not let an AI response modify scene memory directly. Parse it into typed
commands, validate every command, then apply it through the same undoable command
system used by the editor UI.

Fixed: the resolver now recognizes when the player's full footprint sits entirely inside the other collider (which can only happen for a vertical overlap - a wall could only ever clip one edge) and always resolves upward in that case. Also added an explicit Raise/Lower toggle to the Terrain sculpt brush (previously lowering only worked by holding Shift, which turned out to be too easy to miss - Shift now temporarily flips whichever mode is active instead of being the only way to lower).
- **Alpha 0.49** - Real model import: Character menu > "Import Model (GLB/glTF/FBX)..." (previously just an inert placeholder button that did nothing - clicking it never even opened a file dialog). Added Assimp as a new dependency (via the same CMake FetchContent mechanism as every other library here) to parse the actual files. The picked file is copied into `Game/Models/`, then every mesh in its node hierarchy is flattened - with each node's own transform correctly applied (Assimp's row-major/row-vector matrices are converted to glm's column-major/column-vector convention) - into one combined mesh, cached and rendered per-entity the same way Text Mesh and Terrain already are. Picking uses the model's real bounding box, not the ±1 primitive assumption. No materials, textures, or skeletal animation yet - see Known gaps for exactly what that means today.
- **Alpha 0.50** - Bugfix: importing an FBX file could crash the whole editor. Assimp's FBX importer can throw a C++ exception on malformed or unusual input instead of always failing gracefully via a null return, and `loadModelMesh` had no `try`/`catch` around the call - an uncaught exception unwound straight through the ImGui render loop and took the app down. `loadModelMesh` now catches every exception and returns a normal failure result instead, and `appendMeshNode` gained defensive bounds/null checks (out-of-range mesh indices, missing normals, out-of-range triangle indices) as further hardening. Also added 3DS, OBJ, and Blend import support (`ASSIMP_BUILD_3DS_IMPORTER`/`OBJ_IMPORTER`/`BLEND_IMPORTER`, updated file-dialog filter and Character menu label), and auto-frame-on-import: since real-world model files are rarely authored at this editor's small primitive-sized scale, the camera now frames itself on the model's actual loaded bounds right after import instead of staying at the default ~4-unit distance, where a large or off-origin import could be effectively invisible. A model that fails to import (e.g. an old/unsupported FBX format version) now also logs a clear Console error instead of silently leaving an empty entity.
- **Alpha 0.51** - Security hardening: attached Lua scripts could previously reference a file anywhere on disk. `AttachScriptCommand` only ever checked that the file existed, never that it stayed inside the project - a `.lua` path with `..` traversal or an absolute path (e.g. from a shared/untrusted scene file) would attach and run. Added a new shared `gameforger::core::resolveProjectFile()` (Engine/Core) that resolves a path against the project root, requires it to land inside a specific required subdirectory, and optionally checks its extension - the one project-boundary check every asset/script lookup should go through, rather than each call site inventing its own. `CreateScriptCommand` and `AttachScriptCommand` (`EditorScene.cpp`) now both require `Game/Scripts/*.lua` through it, replacing the old, weaker string-prefix `isInsideProject` check (removed). `ScriptRuntime::startScript` independently re-validates the same way immediately before `luaL_loadfile` - this is the actual single choke point every script execution goes through, including scripts referenced by a hand-edited or untrusted scene file loaded straight into `SceneEntity::scripts` with no validation of its own. Also removed the Lua base library's `dofile`/`loadfile` globals: `io`/`os`/`package`/`debug` were already never loaded, but `dofile`/`loadfile` read and execute an arbitrary file by path independently of those, so leaving them in place would have made the path-confinement fix easy to route around from inside a script. Verified live: the existing `fps_controller.lua` prefab still starts normally under Play (`Console` confirms `Started Game/Scripts/fps_controller.lua on entity...`), so legitimate project scripts are unaffected.
- **Alpha 0.52** - Three fixes/additions. (1) Terrain sculpt bugfix: a freshly created terrain started perfectly flat at `heights[]=0.0`, which was also the sculpt brush's lower clamp bound - so "Lower" had nowhere to go on a new terrain (no canyons/riverbeds/lake bottoms possible), only "Raise" ever visibly worked. `heights[]=0.5` is now the flat baseline (matching the Perlin generator's own existing convention) with the mesh Y position computed as `(height - 0.5) * heightScale`, giving Raise and Lower equal headroom in both directions. Note this changes what an already-saved terrain's heights render as - existing sculpted terrains will look different on reload. - **Alpha 0.60** - Two fixes/additions. (1) Bugfix: the editor appeared to "crash"/have memory saturate while painting the terrain with a real-world texture (`EARTH_PATH.png`, 3048x3048) - it wasn't a crash, it was `TerrainTexture.hpp`'s auto-generated normal/height map code running an unoptimized, single-threaded, full-resolution per-pixel loop (twice - normal and height) on the main thread, far worse in a Debug build (no compiler optimizations) than Release. Fixed by capping the resolution that generation actually processes to 1024px on the longest side (`downsampleToMax`, nearest-neighbor, same technique `loadHeightmapImage` already uses) before running those loops - a bump/height map doesn't need full source resolution, and this bounds worst-case cost regardless of how large a texture someone drops in. (2) Extended texturing beyond terrain to any regular object (primitives, imported meshes, text meshes): `SceneEntity` gained `materialLayers` (reuses `TerrainLayerData` - same per-slot diffuse/height texture idea) and `materialBlendWeight` (a constant RGB mix across the whole object, unlike terrain's painted-per-vertex weight, since a cube doesn't have a paintable surface the way a heightmap does). Since none of the 6 shared primitives have real per-vertex UVs, texturing them uses triplanar projection (three axis-aligned planar samples blended by how much the local normal faces each axis) instead of adding a per-shape UV unwrap - a new `texturedMeshShaderProgram_` reuses the exact texture-loading/caching code built for terrain layers (`ensureTerrainLayerTexturesGpu` was already generic, not terrain-specific). Diffuse+height only, no normal-map perturbation for this shader (correct triplanar normal mapping needs each axis's sample reoriented before blending - real extra complexity, deliberately deferred). Inspector's Appearance section (any non-terrain entity) gained the same Built-in/Upload-from-PC texture pickers as Terrain's Paint layers, plus a 3-slider "Mask RGB" control - all-zero (the default) falls back to the existing flat `color`, so nothing already in a scene changes appearance.
- **Alpha 0.59** - Terrain texture painting: the first texture-mapping pipeline in the editor (previously nothing had UVs or sampled a surface texture at all - closes the prerequisite gap that blocked this since Terrain Phase 1). A terrain now has 3 paintable ground layers (`TerrainLayerData`: diffusePath/normalPath/heightPath, mirrors Unity's TerrainLayer asset - each map is an independently-uploadable slot, not one fixed bundle), blended per-vertex by a splat weight (`TerrainData::splatWeights`, RGB per heightmap texel, riding along as a 3rd interleaved vertex attribute rather than a separate splat-map texture, since it's already on the same grid as `heights`). New Inspector "Paint" brush mode (alongside Raise/Lower) with a layer selector and the existing brush radius/strength sliders - `paintTerrainSplat()` mirrors `sculptTerrain()`'s raycast+falloff shape, raising the target layer's weight and renormalizing all 3 to keep summing to 1. Each layer's Diffuse/Normal/Height slot has a Unity-style two-mode picker: browse existing `Game/Textures/` files, or "Upload from PC..." (copies into the project, mirrors `importFontIntoProject`). Leaving Normal/Height empty is not a dead end - `TerrainTexture.hpp`'s `generateNormalMapFromDiffuse`/`generateHeightMapFromDiffuse` derive both from the diffuse texture's own brightness (dark=low, bright=high, standard tangent-space normal encoding) so a layer works immediately with just a color texture and can be upgraded later by filling in real authored maps, no shader changes needed either way. New terrain-only shader blends 3 diffuse/normal/height sets by the interpolated splat weight, perturbs the lit normal by the blended normal map (a direct XY perturbation of the vertex's own normal, not a full tangent-space TBN basis - terrain is close enough to horizontal everywhere it matters), and uses blended height as a subtle shading/AO-like cue rather than true parallax occlusion mapping. Seeded with the user's own `Game/Textures/TEX_PACK_01` pack (Sand/Rock/Earth-Path); a fresh terrain defaults to that 3-layer set. Explicitly scoped out this pass (confirmed via AskUserQuestion): particle FX (smoke, muzzle flash, the pack's `FX_*` sprites) needs an entirely separate billboard/particle renderer that doesn't exist yet - deferred to its own follow-up rather than bundled in. **Known gap**: `GameForgerRuntime`'s `SceneRenderer` was updated to use the new 9-float terrain vertex stride (required - the old hardcoded 6-float stride would have silently corrupted Runtime's terrain rendering the moment any terrain entity loaded) but does not yet sample/blend the splat textures itself - Runtime renders terrain's correct shape and slope-lit shading, just not the painted texture layers, until that duplicated shader path is brought up to parity with the Editor's.

- **Alpha 0.56** - Two correctness fixes in `ViewportRenderer::computeSkinningMatrices` (GPU character-skinning palette), found by an independent audit (`NewAudit.md`, N1/N2) and confirmed by re-reading the code, not just trusted at face value. **N1**: the palette never factored out the scene's own root bind transform (`globalInverseTransform = inverse(scene root's bind pose)`) before combining with each bone's world transform and offset matrix - a no-op for files whose root transform is identity (true for the dancing-man test file, which is why 0.52's live verification didn't catch it), but would visibly mis-scale/rotate/offset skinned meshes from exporters that put a non-identity axis/unit-conversion transform on the root node, even though the static (non-skinned) import path for the same file looks fine. **N2**: when an animation channel exists for a bone but only animates SOME of position/rotation/scale (a legitimate, common export shape), the missing key arrays fell back to a hardcoded identity component (0 translation / identity rotation / unit scale) instead of that bone's own bind-pose value for the missing piece - snapping it to the origin/bind-rotation/unit-scale instead of preserving it. Fixed via a manual TRS decomposition of the bind transform used as the per-component sampling fallback.
- **Alpha 0.55** - Bugfix: Viewport WASD/QE flythrough did nothing even while holding the right mouse button - reported as "still doesn't work" after 0.52's hint text turned out not to be the real gap. Root cause: the flythrough movement block was gated on `!ImGui::GetIO().WantCaptureKeyboard`, but Dear ImGui only clears a text field's keyboard focus on a LEFT click outside it, not a right click - so any previously-focused text field elsewhere in the app (AI Forge prompt, a rename box, the script editor...) kept `WantCaptureKeyboard` true and silently swallowed every WASD/QE press while flying, even though right-click-drag (mouse-look) worked fine since that part of the code never checked the flag. Fixed by dropping that guard specifically for the active-fly movement block - `camera.dragMode` only ever becomes `Fly` via an explicit right-click that already required the viewport to be hovered, which is itself an unambiguous "give keyboard to the camera now" signal; the gizmo-mode hotkeys (W/E/R/T/Y) elsewhere correctly keep their own separate `WantCaptureKeyboard` guard, since those SHOULD stay silent while typing.
- **Alpha 0.54** - Bugfix: a "Ground"-tagged Terrain's Collider did nothing useful for gameplay physics - `resolveBoxCollision` (ScriptRuntime.cpp) built every collider's box from the generic `entity.position +/- entity.scale`, which for a Terrain entity (scale left at its default 1,1,1) collapsed the entire heightmap down to a practically useless 2x2x2 box at the terrain's origin, completely blind to the actual sculpted hills/canyons. Reported as "can't jump" + "I pass through the hills, no collisions are detected" - both were the same root cause: `self.physics:resolve()` almost never actually overlapped that tiny box, so `grounded` stayed false (no jump) except when the player fell all the way down to the FPS controller's flat `position.y <= 0.0` fallback floor, which only lines up with FLAT parts of a terrain, not hills. Fixed by special-casing `other.isTerrain` in `resolveBoxCollision`: sample the real heightmap at the mover's XZ (via a new shared `sampleTerrainHeight` in Terrain.hpp/.cpp, extracted from main.cpp's existing sculpt-brush-raycast copy so both agree with what's actually rendered) and snap the mover to that height, rotation-blind like every other collider here. Terrain colliders now act as a real, hill-shaped floor instead of an invisible point-sized box.
- **Alpha 0.53** - Bugfix: importing a model file that fails to load (no mesh geometry, unsupported format, etc.) froze the whole editor - reported live as "app crashes or memory over-saturates and I can't even click anywhere." Root cause: `ViewportRenderer`'s per-entity GPU-mesh caches (imported meshes AND Text Mesh, same bug in both) only ever short-circuited re-building when `vertexArray != 0` - but a FAILED build never allocates a `vertexArray`, so the guard never triggered and the full (expensive) reimport/rebuild ran again on every single `render()` call, forever, at 60fps. Fixed by tracking "was a build attempted for the current source data" (`loadAttempted`/`buildAttempted`) separately from whether it succeeded, so a failure is cached too and only actually retried when the underlying data (source path / font+content) changes. Reproduced live: the user picked `rp_nathan_animated_003_walking_u3d.fbx` from a character pack that ships separate per-engine "animation only" FBX variants (skeleton + clip, no mesh) alongside the real combined mesh+skeleton file - `loadModelMesh` now also gives a specific message for exactly this case ("looks like an animation-only export variant... check the same folder for a file with the actual mesh") instead of a generic "no mesh data" error, since it's a common, easy mistake with these asset packs, not a corrupt file.
