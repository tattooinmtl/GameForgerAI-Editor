Plus 2,387 insertions / 382 deletions across 23 tracked files, also uncommitted.

Concretely, `git show HEAD:Editor/CMakeLists.txt` lists six source files; the working copy lists
nine. So:

- **A fresh `git clone` produces the August editor** — no Blender integration, no AI Cockpit, no

- **CI has never compiled any of this code.** The workflow at `.github/workflows/ci.yml` builds
  `origin/main`. Every green check on GitHub is a green check on the pre-Phase-A snapshot. The

  Debug-only too.
- The single point of failure for ~3,300 lines of work is one directory on one disk.

`DailyAudit2026-09-05.md` §U-04 looked at the same `git status` and concluded "None of that is
code; just noting so the next `git add -A` is done carefully." That reading is incorrect — the
untracked set is mostly assets and docs *by file count*, but it contains the entire Phase A–C
implementation. This is the correction that matters most in this file.

**Action:** commit the Phase A–D source before anything else in this document.

### A-06 — MED — `models/` is untracked and unignored

```
models/          610 MB, 57 .glb files   -> git check-ignore: NOT IGNORED
```

`.gitignore` covers `/out/`, `*.zip`, secrets and IDE state, but nothing for `models/`. A routine
`git add -A` — the exact command §U-04 warns about — would commit 610 MB of binaries into a repo
whose `.git` is *already* 331 MB. It is also a duplicate: `Game/Models/` is the directory the editor
actually reads (`Editor/src/main.cpp:1276`), root `models/` is not referenced by any code path.

**Action:** either delete root `models/` or add it to `.gitignore` today, before A-01's commit.

### A-10 — LOW — Repo hygiene

- **No `LICENSE` file**, though the initial commit message declares the project "closed/proprietary."
- **No `.gitattributes`.** Every `git diff` emits `LF will be replaced by CRLF` warnings for all 20
  modified files. Line-ending churn will contaminate the first real diff after A-01.
- `.git` is 331 MB, dominated by committed binary assets — a 50 MB normal map, two 45/25 MB FBX
  rigs, a 25 MB `.psd`, 20 MB PNGs. Git LFS was never set up. This is not fixable in place without a
  history rewrite, so the practical call is: **do not add more**, and decide now whether the asset
  packs belong in git at all.

## 4. New-code findings (Phase A–D)

### A-02 — HIGH — Blender MCP runs with no authentication

`BlenderClient::Config` declares `bearerToken` (`Editor/include/GameForger/Editor/BlenderClient.hpp:40`)
and both consumers respect it:

- `Editor/src/BlenderClient.cpp:454` — sends `Authorization` only `if (!config_.bearerToken.empty())`
- `Editor/src/main.cpp:1618,1732` — passes `client.config().bearerToken` to the launcher, which
  writes it into the addon's preferences (`BlenderLauncher.cpp:227-230`)

**Nothing ever assigns it.** `setConfig()` exists (`BlenderClient.cpp:252`) but has no callers in
`main.cpp`. A full-tree grep for `bearerToken` returns exactly the five sites above — declaration,
two reads, two passes-through. It is always empty.

Result: Blender is launched with `p.preferences.auth_token` unset, its MCP server binds
`127.0.0.1:8765` (`BlenderClient.hpp:38`) with no auth, and the editor sends no credential. Any
local process on the machine can drive the MCP surface — including `code.execute_python`, i.e.
arbitrary Python inside Blender with the user's privileges. The header comment at
`BlenderClient.hpp:78` even acknowledges the client will talk to "any process on this port."

**Action:** generate a random token at launcher start, store it in the `Config`, call `setConfig()`
before the first `ping()`. The plumbing is already built; only the assignment is missing.

### A-03 — HIGH — The default provider cannot work for any non-Cockpit AI feature

`AIProviderClient::send()` unconditionally builds an **OpenAI chat-completions** body and an
**OpenAI** auth header:

```
AIProviderClient.cpp:306-310   {"model":..., "messages":[{"role":"system",...},{"role":"user",...}]}
AIProviderClient.cpp:343       L"Content-Type: application/json\r\nAuthorization: Bearer " + key
```

There is no `protocol` branch in `send()` — `parseProvider()` never reads the field at all
(`AIProviderClient.cpp:157-168` reads only `endpoint`, `model`, `apiKeyEnvironmentVariable`).

The default provider is Anthropic, in both sources of truth:

- `Game/AI/Providers.json` → `"activeProvider": "anthropic"`
- `Editor/src/main.cpp:625` → `int selectedProvider = 0`, and index 0 of the hardcoded
  `providers` array (`main.cpp:723-730`) is `anthropic` → `https://api.anthropic.com/v1/messages`

Anthropic's Messages API requires `x-api-key` + `anthropic-version` headers, `max_tokens`, and
`system` as a top-level field rather than a message role. `send()` supplies none of those. So on a
clean install, every `send()` caller fails:

- `Editor/src/ScriptGenerator.cpp:115` — AI script generation
- `Editor/src/AICommandPlanner.cpp:446` — AI Forge command planning
- `Editor/src/AIAnimationGenerator.cpp:167` — AI animation generation
- `Editor/src/main.cpp:2662` — the "Calibrate / Test provider" button, which will report the
  provider unreachable when it is fine

The AI Cockpit is unaffected — it goes through `sendRaw()`, which sends both auth schemes
(`AIProviderClient.cpp:446-451`) and branches the body on protocol (`AICockpit.cpp:959,980`). The
fix is to give `send()` the same treatment `sendRaw()` already has.

Worth noting the structural cause: `main.cpp:723` hardcodes a `constexpr std::array<AIProvider, 8>`
that duplicates `Game/AI/Providers.json`. The UI reads the array; the transport reads the JSON. Edit
one and they diverge silently — and the "Add Custom Provider" popup only *prints a snippet to the
console* for manual pasting (`main.cpp:2593-2607`), so a custom provider can never appear in the
dropdown at all.

### A-04 — MED — `json::parse` has no depth limit

`Engine/src/Editor/Json.cpp`'s `Parser` carries exactly two members — `text_` and `pos_`
(`Json.cpp:73-74`) — and `parseValue` → `parseObject`/`parseArray` → `parseValue`
(`Json.cpp:89,297,351`) recurses with no counter and no cap.

F-11 closed the *entity-hierarchy* depth caps in `GameplayLoop.cpp` and `ModelImport.cpp`. The JSON
parser itself was not covered. It is fed, among other things:

- AI provider HTTP response bodies (`AIProviderClient.cpp:606`, `AICockpit.cpp`)
- Blender MCP JSON-RPC responses (`BlenderClient.cpp:308`)
- every `.scene.json` / `.gfprod` a user opens

An input like `[[[[[…` at ~10–50k nesting overflows the 1 MB default stack and hard-crashes the
process. Reachable from a misbehaving or hostile endpoint, and from any scene file received from
someone else.

**Action:** thread a `depth` counter through `parseValue`, reject past ~200. Roughly a 10-line change
and it matches the depth-cap pattern F-11 already established elsewhere.

### A-05 — MED — Auto-approval is a name blocklist over remotely-supplied tool names

`isDestructiveTool()` (`AICockpit.cpp:57-74`) lowercases the tool name and looks for any of
`delete remove clear overwrite erase purge scene.stop code.execute_python execute_python`.
`requiresApproval()` (`AICockpit.cpp:440-458`) then auto-runs anything that misses.

Two things make this the wrong shape:

1. **It fails open.** A tool named `bpy.run`, `file.write`, `object.set_script`, `scene.replace`,
   `apply_modifier` — none contain a marker, all execute unattended in autonomous mode.
2. **The names are not ours.** The Blender tool catalog is fetched at runtime via `tools/list`
   from the MCP server (`BlenderClient.cpp:300-312`). The gate is deciding whether to auto-execute
   based on a string chosen by the other end of the socket. Combined with A-02 (no auth on that
   socket), a local process can register a benign-sounding tool and get it auto-run.

The `execute_python` special case at `AICockpit.cpp:455` is correct and well-reasoned; the problem
is everything it does not name.

**Action:** invert to an allowlist. The in-editor `scene.*` catalog is fixed and enumerable
(`AICockpit.cpp:206-212` and around), so mark those known-safe and require approval for everything
arriving from `tools/list` by default.

*Checked and clear:* the approval handshake itself is correct. `main.cpp:1922-1939` calls
`approveDestructive()` while still holding `approvalMutex`, so the condition-variable wait at
`AICockpit.cpp:471-475` cannot lose the wakeup on the approve/reject path.

*One residual:* `requestCockpitStop()` (`AICockpit.cpp:506-509`) and `joinCockpitWorker()`
(`AICockpit.cpp:531-534`) both mutate `loopRunning` — a predicate of that same wait — **without**
taking `approvalMutex`. A notify issued while the worker still holds the mutex evaluating its
predicate is lost, and the worker blocks forever. Since `joinCockpitWorker()` at `main.cpp:8163`
runs on shutdown, the failure mode is the editor hanging on exit with its window already gone.
Narrow race, trivial fix: take the lock around the store in both functions.

### A-07 — LOW — Dead configuration in `Providers.json`

Seven of the keys the file advertises are read by nothing:

| Key | Reality |
|---|---|
| `activeProvider` | never read — provider comes from `main.cpp:625`'s `selectedProvider = 0` |
| `localSecretsFile` | never read — path is hardcoded at `AIProviderClient.cpp:300` |
| `timeoutSeconds: 120` | **overridden** — `kHttpTimeoutMs = 30000` (30s), `AIProviderClient.cpp:45` |
| `enabled` | never read — a disabled provider still works |
| `priority` | never read |
| `capabilities` | never read (the `BlenderClient.cpp` hit is unrelated MCP schema) |
| `displayName` | never read — comes from the hardcoded array |

`timeoutSeconds` is the harmful one: a user raising it to 300 for a slow reasoning model still gets
cut off at 30 seconds with a generic "Provider request failed."

### A-08 — LOW — Unescaped JSON in the custom-provider snippet

`main.cpp:2593-2607` builds the emitted JSON by raw `std::string` concatenation of five free-text
`InputText` buffers. A `"` or `\` in any of them yields invalid JSON, which the user then pastes into
`Providers.json` and breaks their config. The file already has `escapeJson()`
(`AIProviderClient.cpp:78`); this path just does not use it.

### A-09 — LOW — Integer underflow in `deriveModelsPath`

```cpp
// AIProviderClient.cpp:506
if (chatPath.rfind(L"/messages") == chatPath.size() - 9)
```

When `chatPath.size() < 9`, `size() - 9` wraps. At exactly 8 characters it wraps to `npos`, which is
what `rfind` returns on no-match — so an 8-character path like `/v1/chat` is misdetected as
Anthropic-native and "Discover Models" refuses to run. Guard with `size() >= 9` first.

### A-11 — INFO — Agent hooks weaken the verification loop

`.claude/hooks/rewrite-build-command.sh` intercepts any command matching
`cmake --build|ctest|msbuild`, pipes it through `filter-noisy-output.sh`, and returns
`"permissionDecision": "allow"`.

Two consequences worth being deliberate about, in a project whose `AGENTS.md` is built around
"verify-driven development":

1. Build and test commands are **auto-approved**, bypassing the permission prompt.
2. Build output is **filtered before the agent sees it** — which is precisely the channel a warning
   regression would arrive on. (The Release results in §2 were captured to a file through a `.bat`
   wrapper, so they are unfiltered and trustworthy.)

Not a defect, but it means "the agent said the build was clean" is a weaker claim here than it looks.

## 5. Test coverage gaps

14 cases, all passing. What they do not touch:

- **`core::resolveProjectFile()` — zero tests.** This is the project's path-traversal confinement
  boundary, used by `ScriptRuntime.cpp:697`, `ViewportRenderer.cpp:1156,1303,1405` and
  `EditorScene.cpp:128,192`. It is the one function in the codebase where a silent regression is a
  security regression, and nothing pins its behaviour. Given F-12 is still open on its Unicode and
  symlink edges, tests should land before that work, not after.
- `AIProviderClient::parseProvider()` — the protocol-confusion bug in A-03 would be caught by a
  single test asserting the Anthropic provider produces Anthropic-shaped output.
- `BlenderClient` JSON-RPC framing, `AICockpit` tool dispatch — no coverage at all (they are
  untracked, so CI could not run them regardless; see A-01).
- JSON parser depth (A-04) and the malformed-input surface generally.

Notes on scope decisions taken during the fixes:

- **A-03 was wider than the finding described.** Fixing only the request would have left the
  feature broken: `extractChatMessageContent()` understood only OpenAI's
  `choices[0].message.content`, so Anthropic replies parsed as empty. The response side was
  fixed too, dispatching on response *shape* rather than configured protocol so that no caller
  needs provider plumbing.
- **A-05's allowlist changes what the "auto-approve" checkbox means.** Autonomous mode alone now
  runs only the seven known-safe editor `scene.*` tools. The checkbox extends that to everything
  else, including discovered MCP tools. Its label and tooltip were updated to say so. This is a
  deliberate behaviour change: the old default auto-ran any tool whose name happened to miss a
  substring blocklist.
- **Reaching `AIChatResponse.cpp` from the test binary** meant compiling that one translation
  unit into `GameForgerTests` (`Engine/CMakeLists.txt`). The Editor target is an executable and
  cannot be linked, and that file's only dependency is Engine's `Json.hpp` — cheaper than
  restructuring Editor into a library.
- **Two large binaries were deliberately left untracked**, per A-10's "do not add more":
  `Game/Branding/gameforgerai-neon-system.mp4` (15 MB) and `Game/Models/CastleHighTides.glb`
  (13 MB). They are still on disk and still unversioned — a decision, not an oversight.

- **A-11.** `.claude/hooks/rewrite-build-command.sh` still auto-allows build and test commands
