## 1. How This Document Works

### 1.1 Ticket ID scheme
- **`T#-#`** — inherited from the archived master plan (`planFix_AGY.v1.2026-08-18.md`), kept unchanged so old discussion/links still resolve. `T3-x` = Tier 3 (Essential Engine Subsystems), `T4-x` = Tier 4 (Editor Workflow), `T5-x` = Tier 5 (Advanced Subsystems), `T6-x` = Tier 6 (Platform Packaging).
- **`DEF-NN`** — from the external gauntlet audit (`PROJECT_AUDIT_GAUNTLET_REPORT.md`), Phase 0 only.
- **`R-NN`** — recovered items: things mentioned in an older audit/plan/design doc that never became a real ticket anywhere until this consolidation. Each cites its source.

### 1.2 Agent roles (Claude / Gemini)
Split by **risk and judgment required**, not by phase — both agents have tickets in nearly every phase:
- **Claude** owns tickets where getting it subtly wrong is expensive: physics/rendering math, security/path-confinement, override-propagation logic (prefabs), state-machine/graph logic (animator, behavior runtime), anything touching Unicode/encoding correctness, and product-shaping design calls (the AI Forge expansion).
- **Gemini** owns tickets that are mechanical, follow an already-established pattern in this codebase, or are additive UI/config plumbing: menu wiring, settings windows, CI config, most small/quick recovered bugfixes, and — once Claude has established a registry/pattern (e.g. the behavior-library runtime in Phase 3) — the repetitive fan-out work of producing many instances of it.
- Ownership per ticket is marked in each phase's table below. Either agent can pick up an unowned or blocked ticket if genuinely idle, but should say so in the ticket's `docs/phases/` file rather than silently reassigning.

### 1.3 Preparation, every phase, before writing code
1. Read this phase's section in full, including its "Prep checklist."
2. Load the skill(s) the checklist names from `C:/.skills/skills/` (see `AGENTS.md` §4 for the full situation matrix).
3. If the phase needs a new third-party library (Jolt, miniaudio, Recast/Detour, etc.), confirm license + integration approach *before* writing code — add it via `FetchContent` in the root `CMakeLists.txt` following the exact pattern already used for `glfw`/`glm`/`assimp`/etc. (see `CMakeLists.txt:60-99`), and write one small standalone spike/test proving the library links and runs *before* wiring it into the full engine. This is the `test-driven-development` skill's discipline applied to a dependency, not just a function.
4. Check `docs/phases/` for any existing file on this ticket (a prior attempt, a blocker someone hit) before assuming you're starting fresh.

### 1.4 Verification protocol — delegate it, don't self-certify
**Every ticket's "done" claim must be checked by a fresh subagent, not the agent that wrote the code.** This applies to both Claude and Gemini:
- **Claude side:** after finishing a ticket, spawn a subagent (Agent tool, `subagent_type: general-purpose` or a review-flavored agent) with a prompt containing only the ticket's acceptance criteria and the files touched — not "here's what I did, confirm it" narration. Ask it to run the build + CTest commands itself and report pass/fail plus anything that looks wrong, as if it had never seen the change being made.
- **Gemini side:** same discipline, using whatever subagent/task mechanism is available in your own tool — spawn one, hand it the ticket's acceptance criteria and the diff, and have it independently run the build/test commands. Don't mark a checkbox based on your own read of your own diff.
- Zero new compiler warnings is part of "done" for every ticket, not just DEF-04's nodiscard cleanup — a ticket that fixes its own bug while introducing a new warning elsewhere is not finished.
- Build/test commands (unchanged from Phase 0):
  ```
  cmd /c '"C:\Program Files\Microsoft Visual Studio\18\Community\VC\Auxiliary\Build\vcvars64.bat" && cd /d C:\GameForgerAI-Editor && cmake --build out/build/windows-x64 --config Debug --target GameForgerEditor GameForgerRuntime GameForgerTests'
  cmd /c '"C:\Program Files\Microsoft Visual Studio\18\Community\VC\Auxiliary\Build\vcvars64.bat" && cd /d C:\GameForgerAI-Editor && ctest --test-dir out/build/windows-x64 -C Debug --output-on-failure'
  ```
  Run Release too (`--config Release`) for anything touching the build system, shaders, or a new FetchContent dependency.

### 1.5 The `docs/phases/` folder
Read `docs/phases/README.md` for the full naming convention (`phaseNN.letter.md`, `.seq` suffix for redo attempts). Short version: when you start or finish a ticket, write a file there and link it from this document's progress table for that phase. This document stays the index; `docs/phases/` holds the actual "what happened" record.

### 1.6 Do not delete, only rename-and-append-version
No file in this project gets deleted as part of planning churn. A superseded plan gets a version-suffixed rename (see §9) and a banner pointing forward; a superseded phase attempt gets a new `.seq` file in `docs/phases/`. This roadmap itself, if it's ever replaced by a `RoadMap<newer-date>.md`, should be renamed `RoadMap2026-08-21.md` stays as-is (it already carries its date in the name) with a superseded banner added at that time — don't delete it either.
